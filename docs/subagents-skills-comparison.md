## 一、Subagent 與 Skill 的核心差異

| 維度           | Subagent（子代理）                                                        | Skill（技能）                                                |
| -------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **本質**       | 獨立的「執行者」<br>（擁有獨立的 context、工具、權限）                    | 被嵌入主代理「知識層」的「指令卡」<br>（內容載入於 context） |
| **執行環境**   | 隔離的 context window（獨立的對話）                                       | 主 context window 中工作                                     |
| **上下文流向** | 中間工作在子 context 內完成，最後僅回傳摘要（`Subagent Return Contract`） | 所有流程都累積在主 context， tokens 持續增加                 |
| **設計意圖**   | **「做事」→ 隔離、專注**<br>如：客觀審查、資料搜尋、複雜推導              | **「怎麼想」→ 指導思考方式**<br>如：規範設計、程式碼撰寫原則 |

### 核心判斷公式

> **「中間過程對主對話是否真有價值？」**
>
> - ✅ 有價值 → 用 **Skill**（讓它在 context 中「想」）
> - ❌ 沒價值 → 用 **Subagent**（讓它去做，回傳結果）

## 二、三種使用方式的差異與適用情境

| 方式             | 類似行為                                       | 差異                                        | 何時使用                                                  |
| ---------------- | ---------------------------------------------- | ------------------------------------------- | --------------------------------------------------------- |
| **自然語言指令** | 讓主代理自己思考、上網搜尋                     | 無結果封裝，結果不確定，容易吃掉大量 tokens | 快速探索、簡單問題、無須複雜流程                          |
| **Skill**        | 像「念一本手冊」<br>主動告訴代理「你要這樣想」 | 結果取決於你寫的知識與規則，適合標準化流程  | 設計流程、撰寫程式碼規範、定義驗收標準                    |
| **Subagent**     | 像「派人去外面處理事情」<br>給它任務，等它回報 | 隔離環境，能限制權限、控制風險              | 風險高的任務（審查、 搜尋、資料分析）、需要多輪對話的任務 |

## 三、舉例說明：研究最新科技趨勢

| 方法                                                 | 操作方式                             | 優點                             | 缺點                                             |
| ---------------------------------------------------- | ------------------------------------ | -------------------------------- | ------------------------------------------------ |
| **自然語言指令**<br>（如：「請幫我查最新科技趨勢」） | 主代理自己上網搜尋                   | 快速、隨意                       | 結果不夠可控、吃掉大量 tokens、無法重複使用      |
| **Skill**<br>（如：`research_latest_trends`）        | 事先定義好搜尋框架、資料來源、格式   | 可重複使用、流程標準化           | 沒有「結果封裝」，大量搜尋後仍會累積在主 context |
| **Subagent**<br>（如：`trend-researcher`）           | 派個「研究員」子代理去搜、分析、匯總 | 結果封裝、權限可控、上下文不吃重 | 需要事先設計子代理角色與流程                     |

## 四、簡單決策框架：什麼時候選哪一個？

1. **要的是「樣板」或「標準流程」？**
   ➜ 用 **Skill**

2. **要的是「獨立執行」+「結果回報」？**
   ➜ 用 **Subagent**

3. **只是想問個問題、看看結果？**
   ➜ 用 **自然語言指令**

## 五、補充：三者的組合模式（進階）

根據最新的「三層組合模式」：

> **Skill + Subagent + MCP = 完整工作流程**

舉例來說：

- `Skill`：定義「翻譯工作流程」規範
- `Subagent`：執行「翻譯」任務，隔離氛圍
- `MCP`：連接外部翻譯 API

## 小結

根據多篇技術文章的觀點，**Subagent ≠ 能力更強的 Skill**，而是兩種在「**上下文策略**」上的不同選擇：

| 選擇           | 適合情境                           |
| -------------- | ---------------------------------- |
| ✅ 用 Skill    | 你要的是「知識」或「流程標準化」   |
| ✅ 用 Subagent | 你要的是「執行」與「結果隔離」     |
| ✅ 用自然語言  | 你要的是「快速探索」與「即時回應」 |

若你希望設計一個可擴展、可控的 AI 系統，建議先從 **Skill** 著手，再視情況「升級」為 **Subagent**，以符合最小成本與最大效益。
