# PocketAgent 三層式路由架構 (Three-Tiered Routing Architecture)

在面對複雜的軟體工程任務（如大範圍重構、全域除錯、跨檔案溯源）時，AI 代理往往會遇到「模型上下文超載 (Context Exceeded)」與「Token 消耗過高」的雙重挑戰。為了解決這些痛點，PocketAgent 借鏡了業界主流 AI 工具的設計哲學，實作了一套靈活且務實的**三層式混合路由架構**。

透過明確區分「指令巨集」、「動態技能」與「系統級子代理」，開發者可以根據任務的複雜度，精準選擇最合適的代理介入層級。

---

## 1. 架構概覽與運作機制

PocketAgent 的 CLI 在接收到使用者的指令（如 `/researcher`, `/factory`, `/plan`）時，會依序透過三種不同深度的層級進行路由解析：

### 第一層：指令巨集展開 (Command Macros)
* **代表範例**：`/plan 實作登入功能`
* **運作機制**：純粹的字串取代 (String Interpolation)。系統會在發送給 LLM 前，將使用者的短指令套用預先定義的 Markdown 模板（如 `commands/plan.md`），展開為包含嚴謹約束條件的長篇 System Prompt，然後直接餵給主代理 (Main Agent)。
* **執行者**：主代理。

### 第二層：動態技能載入 (On-Demand Skills)
* **代表範例**：`/factory 分析專案`
* **運作機制**：系統會將指令轉換為隱含的提示（例如：`「請載入並使用 factory 技能來處理此任務...」`）發送給主代理。主代理在接收到提示後，會自主呼叫 `use_skill` 工具，將數百行的操作手冊 (SOP) 讀進記憶體中，再依照指示按步就班執行。
* **執行者**：主代理（搭配外部工具呼叫）。

### 第三層：系統級子代理 (Zero-Token Subagents)
* **代表範例**：`/researcher 尋找驗證漏洞` 或 `/parallel researcher:任務A | coder:任務B`
* **運作機制**：這是最深層的隔離路由。CLI 在底層攔截到此指令後，**完全不經過主代理的 LLM 推理**，直接在背景啟動一個全新的 `Agent(is_subagent=True)`。該子代理套用專屬的人設與工具，在獨立且乾淨的 Context 下執行。
* **Map-Reduce 彙整機制**：若使用 `/parallel` 平行啟動多個子代理 (Fan-out)，系統會在收集完所有原始報告後，於背景啟動另一個**獨立的輕量彙整代理 (Summarizer/Reducer)** 進行總結 (Fan-in)。最終只將去蕪存菁的報告回傳給主會話，完美阻絕雜訊污染。
* **執行者**：獨立的子代理群 (包含 Worker 與 Reducer)。

### 💡 核心差異解析：預先載入 (Eager) vs 惰性載入 (Lazy) 與自主性
雖然第一層 (Command) 與第二層 (Skill) 都在主代理中執行，但兩者有著本質的差異：
1. **載入時機與 Token 消耗**：
   * **Command** 是**預先載入 (Eager Loading)**。CLI 會在發送前將龐大的模板字串硬塞入 Prompt，無論 LLM 當下是否只需簡短回答，都會消耗固定的大量 Token。
   * **Skill** 則是**惰性載入 (Lazy Loading)**。CLI 僅發送極短的指令（例如 `請載入 factory`），SOP 的數千字內容會保留在硬碟中，直到 LLM **真正發起** `use_skill` 工具呼叫時才會被讀入 Context。
2. **AI 的自主性 (Autonomy)**：
   * **Command** 只能由人類透過 CLI 手動輸入觸發，AI 無法主動展開巨集。
   * **Skill** 與系統底層的 BM25 向量檢索綁定。即使人類沒有輸入 `/factory`，當 AI 從對話中辨識到相關意圖時，亦能透過系統注入的「技能目錄」自主發現並調閱該手冊。

## 2. 三層架構之綜合比較 (差異與優缺點)

| 比較維度 | 第一層：指令巨集 (Command) | 第二層：動態技能 (Skill) | 第三層：子代理 (Subagent) |
| :--- | :--- | :--- | :--- |
| **上下文 (Context) 狀態** | 與主代理共用歷史紀錄 | 與主代理共用歷史紀錄 | **絕對隔離**，擁有乾淨獨立的脈絡 |
| **載入機制與 Token** | 預先載入 (Eager)。耗費固定 Token | 惰性載入 (Lazy)。需耗費 Token 呼叫工具 | Zero-Token 派發，無須主代理思考 |
| **AI 自主性 (Autonomy)** | ❌ 只能由人類手動觸發 | ✅ 可透過 BM25 目錄自主發現與呼叫 | ❌ 系統底層強制攔截，人類專用捷徑 |
| **優點** | 快速防呆、確保模型回覆格式一致。 | 能在了解過去歷史脈絡的情況下，嚴格遵循 SOP 進行工作流協調。 | 極速派發、物理隔離避免主記憶體被搜尋日誌撐爆 (Context Guard)。 |
| **缺點** | 複雜任務容易導致 Prompt 過長。 | 思考過程全留在主視窗，極易加速逼近 Context 上限。 | 缺乏主會話的歷史知識，任務指派必須非常具體明確。 |

### 🎯 適用的情境建議
* **使用 Command (`/plan`)**：當您只需要模型產出特定格式的報告，或是針對日常對話做快速的 Prompt 工程時。
* **使用 Skill (`/factory`)**：當任務需要嚴謹的步驟檢核（如：先規劃、後實作、再 QA），且模型需要回顧稍早的討論決策時。
* **使用 Subagent (`/researcher`)**：當面臨需要大量 `grep_search` 或翻閱巨型文件的「苦工」時。將這類容易產生大量雜訊的任務隔離，是保護主對話清晰度的最佳實踐。

## 3. 業界代理工具的設計借鏡

PocketAgent 的這套混合式架構並非憑空創造，而是深入研究並融合了市面上頂尖工具的長處：

### 🔍 借鏡 1：Antigravity CLI (Google) 的「原生子代理」
* **參考設計**：Antigravity 極度強調「物理隔離的子代理」與「反應式喚醒」。其主代理在委派任務後會進入休眠，避免無用的日誌污染。
* **PocketAgent 實作**：我們的**第三層路由 (`/subagent`)** 正是基於此理念。我們更進一步結合了 CLI 直通機制 (Zero-Token Routing)，讓使用者可以直接介入委派，而不必等待主代理緩慢地推理出「我應該叫子代理來做」。

### 🔍 借鏡 2：Hermes Agent 的「能力抽象與薄入口」
* **參考設計**：Hermes 不把所有規範硬塞在初始 Prompt 中，而是透過目錄約定讓代理在需要時讀取（Router-First）。
* **PocketAgent 實作**：我們的**第二層路由 (Skills 機制)** 完美體現了這點。將厚重的 SOP 寫成 Markdown 文件，透過 BM25 FTS5 檢索動態注入目錄，讓主代理只有在被明確要求（如 `/factory`）或判斷需要時，才動態載入操作手冊。

### 🔍 借鏡 3：Claude Code (Anthropic) 的「巨型脈絡」與 Codex CLI 的「系統攔截」
* **參考設計**：Claude Code 依賴強大的長文本處理能力進行思路鏈推演；而 Codex CLI 則強調在系統前端直接進行意圖識別與程式碼片段檢索 (RAG)。
* **PocketAgent 實作**：我們的主代理保留了 Claude Code 式的連貫思考能力，但為了避免 Context Exceeded，我們引入了 **Context Guard 防護網** 與 **RAG Codebase Search (`indexed_search`)**。當上下文瀕臨極限時，系統會自動攔截並建議退回使用第三層的 Subagent，達成剛柔並濟的管理。

### 結語
單一的路由策略往往有其死角：全靠單一上下文會撐爆記憶體，全靠子代理又缺乏連貫性。PocketAgent 透過這套三層式架構，賦予開發者最精準的控制權，達成效能與智慧的最佳平衡。
